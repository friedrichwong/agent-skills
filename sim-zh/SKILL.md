# 简化技术中文

- **写法**：结论先行，补充关键信息，再写必要说明。用具体动作写清关系；删掉重复与赘述，保留关键条件、范围和证据。
- **适用**：
  - 持续适用于本会话生命周期沟通内容
  - 代码注释、commit message、文档、说明
  - 任务结果汇报、结论
  - 请用户决定或确认的问题
  - 多项工作的总结，例如任务卡、issue、变更
- **不适用**：
  - 代码
  - 原样引用的日志、错误信息、命令输出。
- **约定**：每次输出或写入前自行检查并改写，语言、格式和结构遵守项目约定；注释、提交信息和文档不强套汇报模板。

## 写作规则

- **R1 用词一致。** 同一对象保持同一名称；不同对象不为统一用词而混为一谈。
- **R2 解释必要术语。** 陌生或有歧义的术语首次出现时简短解释；常用词不另设定义。
- **R3 动作具体。** 写对象的具体行为，不用抽象词包装动作。能写具体动作时，不用“优化、处理、支持”代替。常见改写见“动词替换”表。
- **R4 保留字面量。** 界面文案、命令、路径、标识符保持原文；代码、命令、路径和标识符用反引号。
- **R5 拆开名词串。** 连续堆叠的名词改为明确的关系。例如：“终端会话失败反馈界面状态”改为“终端会话失败时的界面状态”。
- **R6 一句一事。** 一句围绕一个事实或动作；关系紧密的条件、原因与结果可以同句，无关事项分开。
- **R7 短而完整。** 长句拆开，不为缩短文字省略关键条件、主体或因果关系；不机械计数字数。
- **R8 优先主动语态。** 写清谁做什么；执行者不明确或不重要时，可以用被动语态。
- **R9 条件在前。** 写“连接失败时，显示错误”，不把条件拖到动作后面。
- **R10 避免双重否定。** 直接写要求或禁止的动作。
- **R11 区分要求强度。** “必须”表示要求，“不得”表示禁止，“建议”表示推荐，“可以”表示允许；不把建议写成强制要求。
- **R12 主体明确。** 省略主体或使用“它、这、该项”会产生歧义时，补出具体对象。
- **R13 一段一主题。** 删掉偏离主题的句子；标题只在有助于阅读时使用。
- **R14 步骤可执行。** 有顺序的步骤用编号，每步一个动作；必要时紧接着说明结果。
- **R15 并列项用列表。** 多项内容影响扫读时用列表；需要比较多个对象的同类信息时用表格，不为短答堆结构。
- **R16 警告先写动作。** 先写必须做或不得做的事，再写不遵守的后果。
- **R17 列举边界明确。** 要求完整的清单不以“等、之类”掩盖遗漏；举例时明确写“例如”，不假装列全。
- **R18 关键信息先行。** 结果写状态和范围，进度写当前动作，排查写原因或尚未确定的部分，决策写待决事项，总结写总体结论或范围；普通解释写核心答复。注释和文档说明先写用途、条件或行为；提交信息先写具体变更。
- **R19 状态限定范围。** 工作状态与验证状态分别表述，含义按下表区分；不强制固定句式，也不禁止“已修改配置”这样的准确写法。
- **R20 验证如实。** 汇报修复效果、运行行为或检查结果时，写检查方法、结果与覆盖范围。资料证据不能代替运行验证，同一检查只列一次。技术说明以实现或已有证据为依据，不臆造检查记录；普通解释、进度、建议和技术说明不强加验证栏目。
- **R21 不写操作流水账。** 不叙述“我先……然后……接着……”，不写客套话、自我评价或重复总结；只保留读者理解、判断和下一步所需的信息。
- **R22 证据可定位。** 关键结论引用来源位置；代码用 `路径:行号`，命令保留实际执行的完整内容，外部资料给链接。不为常识或每句话机械附来源。
- **R23 决策写选项。** 只有确实需要用户取舍时才请求决定；选项编号，每项写动作和后果，推荐项放第一并标注。能从资料或工具确定的事项不转交用户。
- **R24 不确定性明确。** 区分事实、推断和建议。推断写依据与未证实部分；必要时说明确认方法，不用模糊词掩盖证据不足，也不禁止有依据的概率判断。
- **R25 不编造。** 事实来自用户、文件、工具结果或可靠资料；来源没有的内容不写成事实。示例、假设和建议明确标识，不补造数字、检查记录或需求。

## 动词替换

按实际含义改写，不机械替换词语，不补来源没有的行为或数字。

| 冗余或含糊写法 | 改写方式 |
|---|---|
| 对 X 进行修改 / 检查 | 修改 / 检查 X |
| 予以 X / 加以 X / 做好 X 工作 / 完成 X 的操作 | 直接写具体动作 |
| 作出 X 决定 | 决定 X |
| 通过 X 的方式 | 用 X |
| 实现 X 功能 / 优化 X / 处理 X / 支持 X | 写清具体行为、条件或结果 |
| 存在 X 问题 | 写出具体现象 |
| 有一定的 X | 写有依据的数量或具体表现；无依据时不作程度判断 |

## 标点与混排

中文正文默认用全角标点。中文与英文单词、数字之间加一个半角空格；中文与全角标点之间不加空格。用户或项目格式优先；字面量和原样引用不调整内部排版。

## 状态含义

含义固定，措辞可以自然变化。每个状态都对应具体工作或检查范围。

| 状态 | 含义与必要说明 |
|---|---|
| 已完成 | 所述范围达到要求，没有已知结果否定完成；不自动表示经过验证 |
| 部分完成 | 只完成部分要求；写明未完成或失败的部分 |
| 未开始 | 尚未执行所述动作 |
| 进行中 | 动作已开始，尚未结束 |
| 已验证 | 指定检查执行且通过；写方法、结果和覆盖范围 |
| 未验证 | 已知检查未执行；写范围和原因 |
| 失败 | 动作或检查不符合要求；引用关键失败输出，或准确说明观察到的失败现象 |
| 跳过 | 有意不执行；写原因 |
| 阻塞 | 缺少继续所需的条件；写明缺少什么 |
| 未确认 | 证据不足，事实或检查结果不明；必要时写确认方法 |

必需检查未执行或失败时，不宣称整项任务完成。可以说明“代码修改完成”，但同时说明实际验收状态；不得用“完成，未验证”掩盖已知失败。只有来源缺少检查记录时，不能擅自判断检查未执行。

## 输出模板

以下模板用于对用户的回复，按类型选用，可以合并。删除无内容或无助于理解的栏目，同一信息只写一次。普通问答不套报告模板；短答直接写结论与必要说明。注释、commit message 和项目文档说明按项目结构组织，不强加这些栏目。

同类回复默认沿用模板栏目名，例如“改动、验证、未做、待确认”。准确的其他标题也可以使用；用户或项目已有格式优先。

### 进度说明

通常一句话：`<当前状态>：<当前动作与对象>。<必要的阻塞或限制>`。不预告无关操作，也不为进度添加验证栏目。

### 结果汇报

- 首句：工作状态、完成范围与结果；影响验收的失败或限制放在前面。
- **改动**：具体行为变化，必要时给文件路径。
- **验证**：检查方法、结果与覆盖范围；未执行、失败和证据不足分别说明。
- **未做**：范围内未完成的其他事项与原因；检查事项放在“验证”，不重复列出。
- **待确认**：确实需要用户取舍的事项，按决策模板写。

### 排查结论

首句写原因，或明确原因尚未确认。必要时按“现象 → 原因 → 证据 → 验证 → 建议”组织；证据不足时标明推断，不把用户已描述的现象重复一遍。

### 请求决定

首句写待决事项。

1. `<动作>`（推荐）— `<后果或取舍>`。
2. `<动作>` — `<后果或取舍>`。

### 多项总结

首句写总体结论或总结范围。先集中写共同条件，再分组列每项的“问题”和“要做”，最后列待确认事项。原始标题和标识保留，便于检索；需求摘要不冒充实际成果，“要做”写可检查的结果，不自行增加实现手段。

## 改写示例

以下是虚构的写法示例，不是实际检查结果。来源事实：修改了密码框位置逻辑；浏览器检查通过，键盘弹出时密码框不被遮挡；没有真机环境，未运行 iOS 真机检查。

**改写前**

> 我先看了一下键盘适配，然后优化了相关逻辑，改善了输入体验，测试基本通过了，应该没问题。

**改写后**

> 密码框位置逻辑已修改。浏览器检查通过；iOS 真机未验证。
>
> - 改动：键盘弹出时，密码框保持在键盘上方。
> - 验证：浏览器中聚焦密码框并弹出键盘，确认密码框未被遮挡。
> - 未验证：iOS 真机检查——没有真机环境。

示例只声明代码修改与浏览器检查的范围，不宣称整体任务已完成。

## 输出或写入前自检

每次回复发出前，或写入注释、commit message、文档说明前，自行检查并改写，不输出检查过程：

1. 开头是否直接写核心答复、用途或具体变更，且范围明确？
2. 动作是否具体，主体、条件和因果关系是否清楚？
3. 事实、推断和建议是否分清，结论是否超出证据或验证范围？
4. 是否有操作流水账、空栏目、重复或无用内容？
5. 模板是否适合本次回复，术语和字面量是否准确？

发现问题先改写，不把精简工作留给用户。检查以清楚和准确为准，不机械追求短句。
